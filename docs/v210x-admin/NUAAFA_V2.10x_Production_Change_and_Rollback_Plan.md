## 4. 关键回退门禁：禁止旧代码直接读取新事实数据库

**704旧代码不了解`recordSource/publicHistoryVisible`。候选生成私有赛后COMPLETED记录后，旧的历史/赛事/打印查询可能公开其姓名岗位并当作正式选派。禁止“仅切回704应用且继续使用新数据库”。** 这条门禁不因迁移只追加列、旧代码能启动或SQLite完整性PASS而豁免。

安全回退选项必须在发布批准中明确二选一：

1. **整套一致恢复**：保持维护与写入冻结，先把失败候选数据库、媒体和窗口内全部新增/更正/审计完整保存为独立不可覆盖证据；停止应用写入，采用既有可信旧应用与发布前Bf数据库/媒体/必要运行状态成套恢复到新路径，不覆盖或删除失败根。对Bf之后的所有合法新增记录、比分、账号、媒体和补录逐项列出并由管理员核对；不得静默丢弃或自动倒灌到不认识隐私语义的704。检查原管理员/历史/媒体及真实UTC事实后，才经用户批准开放。
2. **另批兼容读取补丁**：如业务不能接受回到Bf的数据时点，维持维护，保全最新库；先为旧应用制作、独立审核和验收可识别赛后来源/可见性的补丁，再申请新的候选身份及操作授权。这不是本任务已批准的自动回退捷径。

若尚未有任何新事实写入，也必须先证明窗口写入为零、备份一致并经批准，才能采用经预演的回退；不能凭推测判断。任何数据库回退都要说明RPO及对窗口内写入的保全，不能只报告“回退成功”。原时间戳/管理员权限/成绩/历史版本不允许靠重seed重建。

迁移部分失败时，保留候选库和失败迁移账本，选择新路径从可信Bf恢复后重新验证正确迁移；不得在生产使用测试脚本的触发器卸载或故障注入语句。隔离测试已证明真实Prisma失败后可按此方式恢复，不等于本轮执行过生产回退。
